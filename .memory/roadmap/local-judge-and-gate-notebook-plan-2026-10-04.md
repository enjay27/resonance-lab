## 1 · What `jaredpalmer/kev` gives (read 2026-10-04, commit `fe64b12`; Apache-2.0)
- **Kev is the model behind `ggml-org/Kev-4B-GGUF`** (that card: `base_model: jaredpalmer/kev-4b`, "automatically converted"): a rank-16 **LoRA adapter + a small pointer head on `Qwen/Qwen3.5-4B-Base`** (0.8B / 9B / 27B too). So both methods run the *same* model and can be compared (bf16 local vs Q4_K_M in llama-server). HF repo `jaredpalmer/kev-4b`: `adapter_model.safetensors` 130 MB + `head.pt` 5 MB + tokenizer; the base (~9 GB bf16) downloads on first load. `kev-0.8b`: 43 MB adapter on Qwen3.5-0.8B-Base (a smoke-test size). Tags `v1.0` fix the weights (`jaredpalmer/kev-4b@v1.0`).
- **Python API, no server.** `kev.checkpoint.Checkpoint(run)` (`run` = a Hub id, `id@revision` or a local dir) `.load(device, LoadOptions(dtype=torch.bfloat16, merge=True))` -> `(tok, model)`; `kev.serve.Server(ck, tok, model, device)` is the serving engine and **`Server.answer(SystemOneRequest)` returns the `/v1/systemone` body in-process** (batching thread, state-prefix cache); `kev.api.SystemOneRequest` / `Choice` / `to_record` / `to_answers` are the request/response shapes; `kev.predictors.LocalPredictor` is the *evaluation* path (fp32-exact, flash/TF32 off: slow, not for us).
- **The unknown of the handoff is answered:** a choice's `confidence` = `(p_max − 1/K) / (1 − 1/K)` (checked: the Julia-1 fixture's .9907 over 4 options gives .98765 = the recorded confidence). Our `margin` (p1 − p2) stays ours.
- **Behaviour that matters for us:** option order can change an answer (README Limitations; `/v1/systemone/permute` averages orders: a robustness probe worth one cell); an object `state` is rendered as labelled text (`channel:\nPARTY\nmessage: ...`), llama-server gives it as JSON text: the two backends see slightly different prompts for the channel; training was English (the base is multilingual: the probe on real Japanese decides); states over 65,536 tokens are refused (not our case).
- **Requirements (pyproject):** Python **>=3.12,<3.14**, `torch>=2.6,<2.9`, `transformers>=5.17,<6`, `peft>=0.21`, `accelerate`, `numpy>=2.5.3` (+ `fastapi`/`uvicorn`, imported by `kev.serve`; `datasets`, `scikit-learn` are core deps we do not need). **This conflicts with both existing stacks** (llamafactory: torch 2.9.1 / transformers 4.57.1; unsloth: torch 2.10 / transformers 4.57.6), so the local judge needs **its own virtualenv** (`.venv-kev`, `requirements-kev.txt`), like the pipelines already do. Kev is not on PyPI: install the pinned commit with `--no-deps` from git and pin the rest ourselves.
- Speed (their numbers, an L4, bf16): ~120-190 ms per request at 100-330 tokens, CUDA graphs and fused Qwen3.5 kernels on by default in serving; the 16 GB RTX card fits Kev-4B bf16 (~9 GB) but **not** next to a training run.

## 2 · Risks, said up front
1. **Windows + CUDA is unverified** for Kev (their tests are Linux / Apple Silicon): Qwen3.5's Gated DeltaNet layers use flash-linear-attention Triton kernels on CUDA (`triton-windows` would be needed, the repo already uses it for torch 2.9); without them transformers falls back to a slow torch path. Find out in P0 on the PC; a slow-but-working fallback is acceptable for the notebook.
2. **The cloud session can probably verify the wiring on CPU with `kev-0.8b`** (`python3.13` and `uv` exist; the HF CDN host is allowed; torch has to come from PyPI because `download.pytorch.org` was blocked, a big download) — try it in P0, and if it is too heavy say `NOT VERIFIED` and leave it to the PC.
3. A notebook kernel in `.venv-kev` must still import the repo's data modules (`gate_judge`, `gate_eval`, ... need only `pyyaml`): keep `sys.path` = repo root, keep every data module free of torch (already true).
4. VRAM: the notebook must free the judge (`del`, `torch.cuda.empty_cache()`) before anything else uses the GPU; say so in a cell.

## 3 · Architecture (small: the seam already exists)
`GateJudge(client, options, cutoff)` only needs `client.choice(state, instructions, options) -> ChoiceAnswer`. So:
- `judge_local.py` (**model part**: lazy `import torch` / `kev` inside the loader, no `main()` side effects) — `LocalKevClient(run, device=None, dtype="bf16", loader=None)` with the same `.choice()` and `.check_server()` (-> the model name); builds a `SystemOneRequest` with one `Choice` question, calls the in-process engine, maps the answer to `ChoiceAnswer`; every failure -> `JudgeError` naming the run. The loader is **injected**, so the pure part (request building, answer mapping, error mapping) is unit-tested with a stub engine on every OS.
- `gate_judge.judge_id(...)` gets a `kind` so `by` stays honest: `systemone:<model>:<hash>` (server) vs `kev-local:<run>@<revision>:<hash>` (local) — the two journals never mix without `--force`; `read_journal` already refuses another `by`.
- `scripts/categorize.py`: `--judge-local RUN` (e.g. `jaredpalmer/kev-4b`, `--dtype bf16|fp32`, `--device cuda|cpu`) **mutually exclusive** with `--judge-url`; everything after the client is built (journal, cutoff, probe, sweep, fallback rules) is shared and unchanged. `scripts/judge_check.py --local RUN`.
- **Notebook** `notebooks/gate_pipeline.ipynb` (committed with outputs stripped, `tests/test_notebooks.py` guards it; kernel = `.venv-kev`), a `BACKEND = "local" | "server"` switch so **one notebook serves both methods** (the server branch is the existing `--judge-url` client; P5).
- Pure helpers for the notebook go in a data-part module `gate_pipeline.py` (tested), like `parameter_test.py` does for the other notebook.

### The notebook's cells (one run = the whole Gate pipeline)
0. kernel/GPU/versions check (venv name, `torch.cuda.is_available()`, `kev` importable, free VRAM). 1. **Parameters** (raw log, sample path, `BACKEND`, `RUN`, dtype, cutoff, `USE_CHANNEL`, recipe name, `RUN_FULL_PASS = False` so Run All cannot start the long pass — same trick as the sweep switch).
2. **Data** (only when it changed): `fetch_data.py` (needs `huggingface_hub` in the venv) -> `validate.py`; show the row count, the **channel mix** (the unified pinned file has none: say so).
3. **Load the judge once** + a three-line smoke check (timing per request).
4. **Draft a labelled sample:** a stratified draw of ~200 distinct raw lines (per rule-baseline root + the judge's guess, seeded) written as `data/eval/gate1-sample.draft.jsonl` with the judge's `category` and the `channel`; **the maintainer corrects the labels in an editor** and saves as `gate1-sample.jsonl` (the judge pre-labels, the human decides; the file is gitignored).
5. **Probe:** rules vs judge on the real sample (`gate_eval` reports), the cutoff sweep, with and without channel (two passes), optionally permutation-averaged. 6. **Pick the cutoff** (a cell prints the line for `config.JUDGE_CUTOFF` / the command to run).
7. **Full pass** over the raw log -> journal (resumable, progress, ETA from the measured speed) -> `categories.jsonl` -> the split by root.
8. **Recipe preview:** the chosen `configs/datasets/*.json` against the categories: selected vs available per category, what would be short (this is the data-side half of G2-3).
9. **Decide / record:** a markdown block for the memory notes (model + `by`, cutoff, sample size, scores, coverage, speed). Free the GPU.
