## 2 · What the gate is, and what it is not
Gate 1 gives every distinct raw message **one root category** (Gate 1-A: a child below it). It runs once over a big log (batch, not live), writes `categories.jsonl`, and a recipe then selects by it. Japanese in, English instructions: no Korean is involved.
It **measures and labels**; it never rewrites a message and never drops one (a message it cannot place stays `uncategorized`). The category is metadata only: it must never enter a training prompt (the app sends instruction + line, `stream-contract.md`).
The judge must **beat the rule baseline on a hand-labelled sample** to be worth a GPU pass. The data never leaves the machine: a local llama-server only, no hosted Jev (maintainer's privacy decision, 2026-10-03).

## 3 · The endpoint (from https://huggingface.co/blog/ggml-org/decision-models-in-llamacpp, 2026-10-02 — read, NOT run)
llama.cpp's server has `POST /v1/systemone` (PR #29818; the server docs hold the reference — **read them first**, see §8). Start: `llama serve -hf ggml-org/Kev-4B-GGUF` (the new unified CLI from llama.app / `llama update`; the maintainer says `llama-server`, check which binary of his build serves it).
Request `{"state": "<text>", "questions": {id: {"type": "choice", "instructions": "...", "criteria": {option: "description", ...}}}}`; `model` picks a model in router mode (ignored with one model loaded).
Types: `choice` (answer `{"type":"choice","choice": top, "probabilities": {option: p}, "confidence": c}`), `noul` (yes/no, **no `criteria`**; answer `{"type":"noul","noul": P(yes)}`), `score` (2-10 ordered levels; `{score, legend, probabilities, confidence}`). Response also has `model` and `usage` (`output_tokens: 0`: no generation, one forward pass).
Several questions of one request are answered independently; Kev-4B, lev and OpenJev read the state once for all of them. **Describe every option** (the article: Julia-1 routed "charged twice" to shipping with bare labels, to billing at 0.99 with descriptions). **The cutoff is per model** (the same vague ticket scored 0.25 on Julia-1, 0.80 on Kev-4B): choose it on our own sample.
Models: Julia-1 144M (mmBERT, 50+ languages, Apache 2.0, 3 ms), Laya 421M (English), Kev-4B (Qwen3.5-4B-Base, English, Apache 2.0, 12 ms), lev 4B (English), OpenJev 27B (en/de/fr/hi/zh/ja, images, **CC BY-NC**, ~16 GB at Q4: does not fit; not a candidate). Japanese is listed for Julia-1 and OpenJev only: whether Kev-4B copes with Japanese is **unknown** — the probe decides. ms figures are from an RTX PRO 6000, not the maintainer's 16 GB card.
**Unknown, do not assume:** how `confidence` is computed (in the article's example, probabilities .9049 / .0676 / .0275 gave 0.8574: not the top probability) — store `probabilities` and compute our own margin (p1 - p2); the error shapes; limits on state / criteria size; whether `criteria` values may be long descriptions with Japanese examples.

## 4 · Architecture
```
raw log (translated or not) --> scripts/categorize.py --judge-url http://127.0.0.1:8080 [--judge-model M] [--cutoff X]   (PC, llama-server up)
        for every DISTINCT line (dataset_recipe.line_key): judge_client.choice(state=line, instructions, criteria=taxonomy descriptions)
        -> data/processed/categories.jsonl   {key, category, by, p, margin}      (read_categories ignores the extras)
        -> preprocess.py --recipe ...   (exists)
```
- `judge_client.py` (pure, stdlib `urllib`, injected `post(url, payload, timeout) -> dict`, no new dependency): `JudgeError`; `SystemOneClient(base_url, model=None, timeout=..., post=None)`; `choice(state, instructions, options) -> ChoiceAnswer(choice, probabilities, confidence)`; `check_server()` = one trivial `noul` question: returns the model name; 404 -> "llama.cpp too old: `llama update`", connection refused -> "is the server running on that URL?". Every failure is a `JudgeError` that names the URL.
- `gate_judge.py` (pure): `choice_options(taxonomy, root=None)` -> {path: description} (the roots, or the children of one root); `instructions` text as a constant whose hash goes into `by` (`systemone:<model>:<hash8>`); `make_predict(client, options, cutoff)` -> `predict(text) -> root | None` (None when the margin is below the cutoff, or the client fails); also returns the probabilities for the file.
- `scripts/categorize.py` gains `--judge-url`, `--judge-model`, `--cutoff`, `--resume`. The judge pass **appends** one row per line and flushes, so it is resumable (skips keys already in the file with the same `by`; refuses to mix with rows of another `by` unless `--force`). `--probe SAMPLE --judge-url ...` prints the baseline's and the judge's report side by side with `gate_eval.format_gate_report`, plus a **cutoff sweep** (accuracy / coverage / precision per cutoff, computed from one pass's cached probabilities): the cutoff is picked on the sample, mind that 200 lines overfit.
- **Gate 1-A (children), a separate PR:** a second `choice` question per root that has children, options = its children; only for lines the first pass put in that root; stored as `root/child`; an uncertain child leaves the root (note: `balanced-v1-detailed` does not cover a root-only line: use `balanced-v1` for root-only data).
- Throughput: only distinct lines are judged (chat repeats a lot); one request per line with one question first (flags such as "contains a game term" are extra questions in the same request later, nearly free for the 4B models).

## 5 · Decisions for the maintainer (proposal in bold; state them in the plan)
D1 the judge decides, the rule baseline only fills in when the server is unreachable, and the two are scored separately on the sample (**yes**). D2 an uncertain line (margin below the cutoff) is left uncategorized, never forced (**yes**). D3 candidates to probe: **Julia-1 and Kev-4B** (Q8), OpenJev out (size, non-commercial licence). D4 Gate 1-A as its own PR after Gate 1 works (**yes**). D5 `by` carries model + prompt hash, `p` / `margin` are stored (**yes**).
**D6, new and open: keep the channel.** The app writes one `dataset_<CHANNEL>.jsonl` per chat channel, but `hf_data.merge_channels` concatenates the rows verbatim, so the merged raw log has no channel (only the file name did). A party or guild channel is a strong hint (recruitment / coordination vs world chat). Option: add a `channel` field to each merged row (changes the raw log bytes and its sha, so one re-fetch with `fetch_data.py --force`) and give it to the judge as context ("channel: party"); whether the models use it is for the probe. Needs the maintainer's OK and its own small PR before G1-3.
